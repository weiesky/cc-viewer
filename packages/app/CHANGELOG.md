### Patch Changes

- 71cee60: fix(ci): close the three gaps that made release failures recur. (1) `bump-homebrew` in release.yml now `needs: npm-publish` (not `publish`) — it was racing the npm registry write and timing out its poll every release (v1.8.8/1.8.9/1.8.10) because it only waited on the GitHub Release job. - feat(chat): backtick-wrapped local file paths in the conversation become clickable when the file actually exists. Inline code spans whose text looks like a local path (strict heuristic: separator or filename extension required; schemes, `..` segments, version/date dot-chains rejected) are tagged at render time with an inert `data-md-path-candidate` marker — the render pipeline stays pure and cache-safe. A `:N` / `:N-M` line suffix (`apps/web/src/.../ChatView.jsx:3012-3015`) is parsed into `data-md-file-line` and the desktop click targets that line via the existing `scrollToLine` viewer plumbing (system-opened types like PDF/Office open externally and drop the line). After mount, ChatView batches candidates to a new `POST /api/files-exists` endpoint (≤50 paths per request, 1024-char path cap, uniform `{exists:false}` for missing/denied/outside-allowlist — no reason leakage, same `isReadAllowed` policy as the read routes) and upgrades only confirmed files with `data-md-file-verified`: dotted underline at rest, solid border + link color on hover (no background change, no hover underline — keeps the text readable), click opens the embedded file viewer via the same pipeline as tool-call file paths (desktop: file tree auto-expanded; mobile: MobileFileExplorer). Non-existent paths stay plain `<code>` with zero behavior change; negative verdicts carry a 30s TTL so a file created after being mentioned still becomes clickable. Read-only surfaces (IM conversation drawer, team session modal/popovers, memory popovers) never get the verified marker and are unchanged.
- feat(chat): markdown links in the conversation no longer navigate away from the app. External links (http/https/protocol-relative/mailto) render with `target="_blank" rel="noopener noreferrer"` and open in a new tab (in the Electron app they are handed to the system browser via a `setWindowOpenHandler` guard; same-origin windows such as the log viewer still open in-app). Local file links (absolute/relative paths and `file://` URIs) are tagged with a normalized `data-md-file` path and open in the embedded file viewer — same pipeline as tool-call file paths, with the file tree auto-expanded; on mobile they open the mobile file explorer. In read-only surfaces where in-app opening isn't wired (IM conversation drawer, team session modal/popovers), local file links are swallowed instead of navigating away. Anchors and other schemes keep their previous behavior.
- feat(skills): all three skill-add entries (folder / .zip / SKILL.md) now share one strict server-side spec check: SKILL.md frontmatter must contain a valid `name` and a `description` (new error codes `INVALID_FRONTMATTER` / `MISSING_NAME` / `INVALID_NAME` / `MISSING_DESCRIPTION`; intentional behavior change — loose installs that previously fell back to the file/zip name are now rejected). Both upload entry points (user-level and per-IM) map the codes to the same localized messages, and the frontmatter parser now tolerates CRLF line endings (Windows-authored SKILL.md).
