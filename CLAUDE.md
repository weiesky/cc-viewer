When adding new interactive controls, remember to add corresponding i18n entries. The project has two separate i18n files: `apps/web/src/i18n.js` (frontend/React components) and `packages/app/server/i18n.js` (server-side/CLI). Add keys to the correct file based on where the translation is used.
This repository is a pnpm monorepo (A2 split): the publishable package is `packages/app/` (name `cc-viewer` — server + cli + findcc + root shims; its assembled layout IS the npm tarball layout), `packages/core/` holds the shared isomorphic judgment modules (`@ccv/core`, private — request classification, teammate detection, session boundaries, context rules, etc.; imported everywhere as `@ccv/core/<name>` and shipped inside the tarball via `bundledDependencies` — npm pack follows the pnpm workspace symlink, verified on npm 11.x), `packages/content/` holds the bundled content assets (`@ccv/content`, private — `concepts/`, `ultraAgents/`, `server/imPreset/`, `server/imSkills/`; copied into `packages/app/` by `assemble-dist.mjs` at build/pack time, probed live from `packages/content/` in dev via `server/_paths.js`), `apps/web/` is the private frontend build unit (`@ccv/web`), `apps/electron/` the desktop build unit (`@ccv/electron`). Tests live in per-package `test/` dirs (`packages/app/test/`, `apps/web/test/`, `apps/electron/test/`, `packages/core/test/`, `packages/content/test/`) — each holding the tests for that package's code — plus the root `test/` for cross-package integration tests and repo-level guard tests only; root `node --test` auto-discovers all of them.
After completing any code changes, automatically run `pnpm run build` to rebuild the project.
The repo uses pnpm (pinned via the `packageManager` field; settings in `pnpm-workspace.yaml`): install dependencies with `pnpm install`, and never commit `package-lock.json`. Dev toolchain floor is Node >=22.13 (pnpm 11 hard-requires it; CI uses Node 24). Corepack is bundled with Node <=24 and auto-provisions the pinned pnpm; on Node >=25 (Corepack removed) install it with `npm i -g pnpm@11.22.0`. Any new dependency that ships an install/postinstall script must be added to `allowBuilds` in `pnpm-workspace.yaml`, or `pnpm install` hard-fails with ERR_PNPM_IGNORED_BUILDS. npm is still used for `npm publish --provenance` (OIDC trusted publishing); the release.yml Electron build job also runs on pnpm with the default isolated linker (hoisted was spike-verified but rejected for CI — see the A2 implementation record in `docs/refactor/pnpm-monorepo-migration-plan.zh.md`).
The test suite has two tiers: `pnpm run test` is the fast in-process unit tier for the development loop; `pnpm run test:cli` additionally runs the CCV_TEST_CLI-gated CLI/server integration suites (this is what CI runs). When committing code to GitHub, always run `pnpm run test:cli` first to ensure all tests pass; for new server-side scripts (any *.js under `packages/app/server/**`), add corresponding unit tests in the packages/app/test/ directory; update history.md accordingly, and update README.md with translation into all i18n supported language versions if needed. Import direction in `packages/app` (and from `apps/web/src` into it) is governed by the boundary gate `pnpm run verify:boundaries` (layering contract: `docs/refactor/package-boundaries.zh.md`, exceptions: `scripts/boundary-allowlist.json` — a ratchet, shrink-only via `node scripts/verify-boundaries.mjs --write`); the gate runs in every `pretest*` hook, so new cross-layer imports will fail the test suite.
Before publishing to npm, check if any new top-level files in `packages/app/` (e.g. the `cli.js` bin entry, `findcc.js` fork-adapter, root shims `server.js` / `interceptor.js`) are missing from `packages/app/package.json`'s `files` array; the published manifest must never contain `workspace:`/`catalog:` specifiers (assemble-dist.mjs guards this at pack time).
When adding node_modules dependencies, be sure to distinguish between devDependencies and dependencies.
When submitting code to GitHub or npm, always consult the user. Unless the user explicitly prompts you to submit, you should always ask the user before submitting. Don't auto-commit/push/publish — always ask first
Do not increment the version number arbitrarily; versions are bumped by `pnpm changeset version` at release time (which consumes changeset files and regenerates `packages/app/CHANGELOG.md`), never by hand-editing `packages/app/package.json`.
Versioning uses Changesets (stage A3, config in `.changeset/config.json`): any feature/fix change that touches `packages/app/` or `packages/content/` (both feed the published tarball) must include a changeset file (create one with `pnpm changeset`). Only the `cc-viewer` package is versioned — `@ccv/web` / `@ccv/electron` / `@ccv/content` / `@ccv/core` stay static at `0.0.0` (`privatePackages.version: false`; plain-version internal deps like `@ccv/core` are kept out of the changesets graph via `bumpVersionsWithWorkspaceProtocolOnly: true`). For `pnpm-lock.yaml` merge conflicts, don't hand-edit the lockfile: check out either side, run `pnpm install` to re-resolve, and commit the regenerated file.
Use English for all code comments, commit messages, and inline documentation — avoid mixing languages in the same codebase.
Swallowed catch blocks with diagnostic value (SSE/WS event parsing, entry ingest, state updates, fetch handling — anything where a throw means lost data or broken UI) must call `reportSwallowed(tag, err)` from `@ccv/core/error-report` (web components may keep using the `apps/web/src/utils/errorReport.js` shell) instead of silently swallowing; purely-benign best-effort guards (localStorage, tabBridge IPC, revokeObjectURL, listener cleanup) stay bare `catch {}`.
